# AGENTS.md

用于减少大语言模型常见编码错误的行为准则。可根据需要与项目专属指令合并使用。

**取舍：**这些准则更重视谨慎，而非速度。对于简单任务，请自行判断如何应用。

## 1. 先思考，再编码

**不要擅自假设。不要掩盖困惑。明确说明取舍。**

开始实现前：
- 明确说明你的假设。如果不确定，就提问。
- 如果存在多种理解方式，将它们列出来，不要默默选定其中一种。
- 如果有更简单的做法，就说出来。必要时提出异议。
- 如果有不清楚的地方，先停下来。指出困惑所在，并提问。

## 2. 简单优先

**只写解决问题所需的最少代码。不做推测性的扩展。**

- 不添加用户未要求的功能。
- 不为仅使用一次的代码引入抽象。
- 不添加用户未要求的“灵活性”或“可配置性”。
- 不为不可能发生的情况编写错误处理。
- 如果你写了 200 行，而 50 行就能解决，就重写。

问自己：“资深工程师会认为这过于复杂吗？”如果会，就简化。

## 3. 精准改动

**只改必须改的地方。只清理自己的改动造成的问题。**

编辑现有代码时：
- 不要顺手“改进”周边的代码、注释或格式。
- 不要重构没有问题的部分。
- 遵循现有风格，即使你自己会采用不同的写法。
- 如果发现无关的死代码，指出即可，不要删除。

当你的改动导致代码不再被使用时：
- 删除因**你的改动**而不再使用的导入、变量和函数。
- 除非用户要求，否则不要删除原本就存在的死代码。

检验标准：每一行改动都应能直接对应到用户的请求。

## 4. 目标驱动的执行

**定义成功标准。循环推进，直到验证通过。**

将任务转化为可验证的目标：
- “添加校验” → “为无效输入编写测试，再让测试通过”
- “修复这个 bug” → “编写能复现该问题的测试，再让测试通过”
- “重构 X” → “确保重构前后测试均通过”

对于包含多个步骤的任务，先给出简短计划：
```
1. [步骤] → 验证：[检查项]
2. [步骤] → 验证：[检查项]
3. [步骤] → 验证：[检查项]
```

明确的成功标准能让你独立迭代。模糊的标准（如“让它能用”）则需要不断澄清。

---

**这些准则发挥作用的标志：**差异中不必要的改动更少，因过度复杂而重写的情况更少，而且澄清问题发生在实现之前，而不是出错之后。
