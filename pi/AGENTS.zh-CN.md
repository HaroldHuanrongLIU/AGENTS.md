# 开发规则

## 对话风格

- 回答简短、精炼。
- 提交、issue、PR 评论和代码中不使用表情符号。
- 不写空话或过度热情的填充文字（例如写“Thanks @user”，而不是“Thanks so much @user!”）。
- 只写技术性内容，直接表达。
- 使用简洁、清晰、简单的语言。无法避免的术语，应先定义再使用。
- 解释较复杂的设计和问题时，按“问题 → 具体示例或简短执行过程 → 解决方案”的顺序组织。说明方案为什么必要，并区分哪些复杂度是可选的。
- 优先描述具体行为和小例子，而不是抽象总结、密集术语或没有解释的变更列表。
- 用户提出问题时，先回答，再编辑或执行实现命令。
- 回应用户反馈或分析时，先明确说明同意还是不同意，再说明做了什么修改。

## 代码质量

- 在进行大范围变更前、编辑尚未完整查看的文件前，以及被要求调查或审计时，完整阅读文件。大范围修改不能仅依赖搜索片段。
- 除非绝对必要，否则不使用 `any`。
- 仅有一个调用位置的单行辅助函数应内联。
- 到 node_modules 中查看外部 API 类型，不要猜测。
- **禁止内联导入**（`await import()`、`import("pkg").Type`、动态类型导入）。只使用顶层导入。
- 在 `packages/coding-agent` 中，通过 `src/config.ts` 的辅助函数解析包资源。不要直接使用 `__dirname`；这些辅助函数会兼顾源码检出、npm 安装和独立二进制文件。
- 绝不通过删除或降级代码来修复过时依赖导致的类型错误；应升级依赖。
- 根配置检查的代码（`packages/*/src`、`packages/*/test`、`packages/coding-agent/examples`）仅使用可擦除的 TypeScript 语法（Node 仅剥离类型模式）：不得使用参数属性、`enum`、`namespace`/`module`、`import =`、`export =` 或其他需要生成 JS 的结构。使用显式字段并在构造函数中赋值。
- 删除看起来有意保留的功能或代码前，必须询问用户。
- 除非用户要求，否则不要保留向后兼容性。
- 绝不硬编码按键检查（例如 `matchesKey(keyData, "ctrl+x")`）。将默认值添加到 `DEFAULT_EDITOR_KEYBINDINGS` 或 `DEFAULT_APP_KEYBINDINGS`，使其保持可配置。
- 绝不直接修改 `packages/ai/src/models.generated.ts`；应更新 `packages/ai/scripts/generate-models.ts`，然后重新生成。生成后的 `models.generated.ts` diff 始终可以包含在变更中，即使重新生成带来了无关的上游模型元数据更新。`packages/ai/src/providers/data/` 中生成的模型数据已被 gitignore 忽略：绝不暂存，也不要在 git 历史中查找。

## 命令

- 修改代码后（文档修改除外）：运行 `npm run check`，保留完整输出，不使用 tail。提交前修复全部错误、警告和提示。该命令不运行测试。
- 除非用户要求，否则绝不运行 `npm run build` 或 `npm test`。
- 绝不直接运行完整 vitest 套件：它包含在存在端点 / 认证环境变量时会启动的端到端测试。要运行全部非端到端测试，从仓库根目录运行 `./test.sh`。否则，从包根目录运行指定测试：
  - Vitest：`node "$(git rev-parse --show-toplevel)/node_modules/vitest/dist/cli.js" --run test/specific.test.ts`
  - `packages/tui`（`node:test`）：`node --test test/specific.test.ts`
- 如果创建或修改了测试文件，运行它，并迭代测试或实现，直到通过。
- 对 `packages/coding-agent/test/suite/`，使用 `test/suite/harness.ts` 和模拟提供商。不得使用真实提供商 API、密钥或付费 token。
- 为修复 GitHub issue 编写回归测试时，在测试旁添加包含该 issue 编号的注释。
- 临时脚本应通过 `write` 写入临时文件（例如 `/tmp`），运行，必要时编辑，完成后删除。不要在 `bash` 命令中嵌入多行脚本。
- 除非用户要求，否则绝不提交。

## 依赖和安装安全

- 将 npm 依赖和锁文件变更视为需要审查的代码。直接注册表依赖（包括内部工作区依赖）必须固定到精确版本。
- 更新 `undici` 时，**必须**阅读目标版本的变更日志 / 发布说明，并在更新前评估是否有任何变化可能影响功能。
- 本地安装 / 更新使用 `npm install --ignore-scripts`；干净安装 / CI 式安装使用 `npm ci --ignore-scripts`。除非用户要求，否则不运行生命周期脚本。
- 依赖元数据变化时，通过 `npm install --package-lock-only --ignore-scripts` 刷新 `package-lock.json`。
- 如果 `packages/coding-agent/install-lock/` 需要重新生成，运行 `node scripts/generate-coding-agent-install-lock.mjs`（通过 `--check` 或 `npm run check` 验证）。带生命周期脚本的新依赖需要审查，并在该脚本中添加显式允许列表条目；绝不悄悄添加。
- pre-commit 会阻止锁文件提交，除非设置 `PI_ALLOW_LOCKFILE_CHANGE=1`。只有用户希望提交锁文件变更时，才能放行。

## Git

同一 cwd 中可能同时运行多个 pi 会话，各自修改不同文件。影响你自己的变更之外的未暂存、已暂存或未跟踪文件的 Git 操作，会覆盖其他会话的工作。遵循以下规则：

提交时：

- 仅提交你在**本次会话**中修改的文件。
- 使用显式路径暂存（`git add <path1> <path2>`）；绝不使用 `git add -A` / `git add .`。
- 提交前运行 `git status`，确认只暂存自己的文件。
- `packages/ai/src/models.generated.ts` 始终可以与你的文件一起包含在提交中。
- 消息格式：`{feat,fix,docs}[(ai,tui,agent,coding-agent)]: <commit message> (optionally multiple lines)`。消息应信息明确且简洁。

绝不运行以下命令（会破坏其他智能体的工作或绕过检查）：

- `git reset --hard`、`git checkout .`、`git clean -fd`、`git stash`、`git add -A`、`git add .`、`git commit --no-verify`。

如果发生 rebase 冲突：

- 只解决你修改过的文件中的冲突。
- 如果冲突出现在你未修改的文件中，中止并询问用户。
- 绝不强制推送。

## Issue 和 PR

贡献者准入机制（自动关闭工作流、`lgtm`/`lgtmi`、质量标准）见 `CONTRIBUTING.md`。

审查 PR 时：

- 除非用户明确要求，否则不要运行 `gh pr checkout`、`git switch`，也不要以其他方式将工作树切换到 PR 分支。
- 使用 `gh pr view`、`gh pr diff`、`gh api`，以及针对已获取引用的本地 `git show`/`git diff`，在不切换分支的情况下检查 PR 元数据、提交和补丁。
- 如果需要 PR 文件内容，将其获取 / 读取到临时文件中，或使用 `git show <ref>:<path>`，不要切换分支。

创建 issue 时：

- 为受影响的包添加 `pkg:*` 标签（`pkg:agent`、`pkg:ai`、`pkg:coding-agent`、`pkg:tui`）；所有适用标签都要添加。

发布 issue / PR 评论时：

- 将评论写入临时文件，再通过 `gh issue/pr comment --body-file` 发布（绝不通过 `--body` 传入多行 Markdown）。
- 评论保持简洁、技术性，并采用用户的语气。
- 每条 AI 发布的评论末尾，都要添加原始提示词指定的 AI 生成声明行（例如 `This comment is AI-generated by `/wr``）。

通过提交关闭 issue 时：

- 在消息中包含 `fixes #<number>` 或 `closes #<number>`，使合并后自动关闭 issue。多个 issue 需要逐一重复关键字（`closes #1, closes #2`）；共用关键字（`closes #1, #2`）只会关闭第一个。

## 变更日志

位置：`packages/*/CHANGELOG.md`（每个包一份）。

`## [Unreleased]` 下的章节为：`### Breaking Changes`（需要迁移的 API 变更）、`### Added`、`### Changed`、`### Fixed`、`### Removed`。

规则：

- 所有新条目都放在 `## [Unreleased]` 下。先完整阅读该章节，再追加到已有子章节，绝不重复创建子章节。
- 已发布版本章节（例如 `## [0.12.2]`）不可变更，绝不修改。
- 工作目标分支不是 `main` 时，不创建变更日志条目。

署名：

- 内部贡献（来自 issue）：`Fixed foo bar ([#123](https://github.com/earendil-works/pi/issues/123))`
- 外部贡献：`Added feature X ([#456](https://github.com/earendil-works/pi/pull/456) by [@username](https://github.com/username))`
